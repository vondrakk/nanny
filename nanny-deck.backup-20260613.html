architecture

One server between your monitoring and your tools

Ships as one localhost/nanny:bundle podman image (nanny + Prometheus + Alertmanager + blackbox). Validated against a real Icinga: 576 hosts / 4,714 checks.

the core loop

What happens when an alert fires

An operator who claims or acks during the hold cancels the auto-page — nanny sees a human is on it.

the key idea

Adaptive paging: learn what self-resolves

  • Each incident's outcome is recorded per alertname/service signature.
  • If a signature historically clears itself — ≥3 samples, ≥60% self-resolve — nanny holds for the p90 self-resolve time + 30s before paging.
  • Unknown/flaky signatures get the default 120s; cap is 900s.
  • The page fires only for things that actually need a human.
Purely statistical — the hold is learned from history, not the model's opinion. Transparent and explainable.
the triage agent

A read-only investigator with four tools

📡

get_icinga_state

Live host + every service check — "is the whole box down, or one check?"

📚

search_confluence

Finds the runbook; the service's notes_url is also fed in up front.

🗂️

search_jira

Prior incidents for this service and how they resolved.

📜

fetch_logs

Tails allow-listed logs over a locked-down SSH forced command. No shell, ever.

Guardrails: the model never gets a raw shell; every tool call is written to a per-incident audit trail; the loop is turn-capped. It proposes what a human should do — it does not remediate.
the brain is a choice

Cloud, local, or no LLM at all

☁️

Cloud Claude

Default. Strongest reasoning. Per-incident token cost; data leaves the network.

🖥️

Local model

Any OpenAI-compatible server (Ollama/vLLM). Fully offline, in-network.

🚫

No LLM none

Deterministic triage: gather live state, runbook, prior incidents, self-resolve history — still tickets & pages. Zero tokens.

Same pipeline, three brains. Adaptive paging and ticketing don't depend on an LLM — so cost and data-egress are a dial, not a requirement.

deployment & scale

Stateless on Kubernetes — built, verifying on a cluster

  • Single-node mode: in-memory state + local files — the dev / one-team default.
  • Now built: stateless replicas on OpenShift/RHOS, all shared state in a CloudNativePG Postgres cluster — any pod serves any request.
  • The hard part — the delayed page — is a page_at column + a reconciler every replica runs (FOR UPDATE SKIP LOCKED) → paged exactly once, no leader election. Unit-tested on the in-memory backend.
  • Packaged as a Helm chart + CNPG Cluster CR (helm-lint/template clean); logs forward as JSON/syslog.
Status: all 4 phases built — store layer + schema, package split, state wired through the store + paging reconciler, and the Helm chart + CNPG CR. Not yet proven on a live cluster: the Postgres backend and a real multi-replica exactly-once paging run — that's the step between here and production.
engineering

Deliberately small and legible

  • Python, stdlib HTTP server, no web framework.
  • Console is hand-written HTML/CSS/JS — zero JS dependencies, no build step.
  • Single supervised image; runs non-root (uid 10001).
  • Brain-agnostic: cloud / local / none. Logs forward as JSON or syslog.

Honest trade-off

"Small and legible" started as one file, single node. The Kubernetes/CNPG work (slide 11) is what turns it into a horizontally-scalable, durable system — now built, with a live-cluster verification pass still to go.

security audit — still open

What remains — no hiding it

🔐

F6 · TLS verification

Icinga TLS can be disabled/downgraded (ICINGA_INSECURE, legacy ciphers). Needs default-verify + pinned CA.

🎭

F7 · CSRF

No CSRF/Origin check on JSON mutating endpoints yet.

🧠

F10 · Prompt injection

Attacker-influenced alert text reaches the LLM; needs delimiting/guarding.

🗄️

F11 · Durable audit (full)

Forwarding done; a tamper-evident store + verified operator identity → SIEM is the rest.

Plus low-severity items: error-message leakage (F12), query escaping (F13), dependency pinning (F14), scan-pivot exposure (F15). Full report: SECURITY_AUDIT.md.

honest limitations

What can go wrong

🧠

LLM is fallible

Triage can be wrong or vaguely confident; prompt-injection risk (F10) and token cost. Treat its analysis as a hint. (Or run none.)

🌐

Environment-bound networking

In the laptop demo the rootless-container→VPN path is intermittent (Icinga & LDAP both needed retries). A real in-network deploy avoids it.

🗄️

HA: built, not cluster-proven

The stateless/CNPG work (slide 11) is built but not yet verified on a live cluster — single-node in-memory stays the proven default until then.

🧪

Maturity

A capable single-author tool, hardening fast — not yet a battle-tested product across teams.

compliance & fit

SOC 2: closer, not certified

Logical-access (CC6) gaps are largely closed — auth, expiry, rate-limit, signed webhooks. Remaining: CC7 durable/tamper-evident audit (forwarding done; SIEM + verified identity pending), plus F6/F7.

Good fit today

  • ✓ A single ops team's on-call, behind a VPN
  • ✓ Cutting page-fatigue + auto-documenting incidents
  • ✓ Teams who want a legible, self-hosted tool — cloud, local, or no LLM

Not yet a fit

  • ✗ Internet-exposed without F6/F7 closed
  • ✗ Multi-replica HA until the CNPG migration is verified on a cluster
  • ✗ "Set it and forget it" auto-remediation (by design, it doesn't)
